# Evaluating Deal Q&A retrieval

Deal Q&A worked in manual testing, but "works when I try it" is not a measurement. This is
how retrieval is measured, what the current numbers are, and what earlier rounds of
measurement changed.

**Shipped pipeline:** bge-m3 embeddings (local `tei-embedding`) → pgvector cosine search
over the deal's chunks → cross-encoder rerank of the top 30 (`BAAI/bge-reranker-base` on
`tei-rerank`) → `MinScore 0.35` / `RelativeFloor 0.55` → `MaxContextChunks 12` → Claude.
The constants live in
[RetrievalOptions.cs](../src/AiService/AiService.Business/Retrieval/RetrievalOptions.cs).

**Current numbers** (re-measured 2026-10-04 on that exact stack):

| | |
|---|---|
| retrieval recall@final (80 answerable questions) | **1.000** |
| off-domain questions rejected before reaching the model | **10/10** |
| in-domain but unanswerable questions declined by the model | **10/10** |
| answers stating the expected value | **80/80** |
| faithfulness (LLM-judged, mean of 3 passes) | **0.973** ± 0.007 |
| median / p95 search latency | 2.31 s / 3.35 s |

Every number in this doc was measured on that stack, including the experiments behind
stages that were tried and dropped ([History](#history)). The exceptions are a few numbers
from before the switch to bge-m3, when embeddings were OpenAI's `text-embedding-3-small`;
each is labelled as such where it appears.

## Method

RAG fails in two independent places, and one number hides which:

1. **Retrieval**: did the right text reach the prompt?
2. **Generation**: given that text, was the answer correct and grounded?

They are measured separately, by two scripts that share a question set but nothing else.

### The question set

100 labelled questions ([`scripts/eval-questions.json`](../scripts/eval-questions.json)),
generated by [`build_eval_set.py`](../scripts/build_eval_set.py) from the corpus itself.

The corpus PDFs are templated: every document carries a summary block of `label` / `value`
line pairs, so ground truth is *extracted*, not hand-written. Over all 521 PDFs every label
used resolves in 100% of its documents and appears exactly once. All 100 generated
questions were verified against their source PDF (label and expected value both on the
cited page), with zero failures.

Two quality filters shaped which labels are usable:

- **Low-variance labels are excluded.** `Standard` is `ASTM E1527-21` in 43/43 Phase I
  reports. A question whose answer is identical for every property can be answered from
  priors, or from the *wrong* property's document, and would score as correct while
  proving nothing. Everything kept varies across ≥37% of the corpus.
- **Question text paraphrases the label** ("WALT" → "weighted average lease term"), so the
  eval isn't measuring literal string overlap between query and chunk.

Five slices, because they fail differently:

| Slice | n | Built from | Correct behaviour |
|---|---|---|---|
| `single-fact` | 40 | Auto-extracted label/value pairs | Retrieve the chunk holding the figure |
| `table-lookup` | 20 | Rent-roll per-tenant rows | Same, on numeric tables |
| `cross-document` | 20 | A figure two documents *disagree* about | Retrieve **both** chunks |
| `unanswerable` | 10 | Hand-written, in-domain, absent | Decline |
| `off-domain` | 10 | Hand-written nonsense | Rejected by `MinScore` |

`cross-document` uses only pairs that genuinely conflict (OM-vs-rent-roll occupancy differs
in 85/85 properties, OM-vs-LOI price in 62/62). They are scored with strict set-recall:
retrieving one of the two required chunks is a failure, because the answer *is* the
comparison.

### The harnesses

**[`eval_retrieval.py`](../scripts/eval_retrieval.py)**: retrieval only. Stdlib-only, no
LLM. Sends each question to `/ingestion/v1/search`, then re-runs `RetrievalService`'s filter
chain in Python. That duplicates ~20 lines of C#, deliberately: with the filters in the
harness a parameter sweep is a loop rather than a rebuild-redeploy cycle. The ranked fetch
is cached per question, so a 36-config sweep costs 100 searches, not 3,600.

**[`eval_ragas.py`](../scripts/eval_ragas.py)**: generation, through the real
`/ai/v1/deals/{id}/ask` endpoint. Deterministic checks plus RAGAS for the metrics that need
an LLM judge (`Faithfulness`, `ResponseRelevancy`). Answers come from `claude-sonnet-5`; the
judge is OpenAI `gpt-4o` via LiteLLM's `judge-default` route, because a model judging its
own family's output is biased toward it.

**[`check_retrieval_regression.py`](../scripts/check_retrieval_regression.py)**: a gate.
The shipped config must reproduce a frozen reference
([`retrieval-baseline-reference.json`](../scripts/retrieval-baseline-reference.json)) on
every recall metric and every per-question decision. Back-to-back runs with reranking on
are identical, so exact match is the right tolerance.

Corpus covered: 428 documents, 1,147 chunks, on the 54 of 83 properties that have a deal to
attach documents to.

## Retrieval results

### 1. `MinScore` has a narrow window, and 0.375 was just outside it

`MinScore` is an absolute cosine floor. Its only job is rejecting off-domain questions; it
should never cut a chunk that a real answer needs. On bge-m3 those two requirements leave a
gap of 0.025:

| | top score |
|---|---|
| highest off-domain question (*"Explain how a transformer neural network works."*) | 0.340 |
| weakest gold chunk any answer needs (OM asking price, cross-document) | 0.365 |

Fine sweep, reranking on, `RelativeFloor 0.55`, `k=12`:

| MinScore | single-fact | table | cross-doc | **overall** | off-domain rejected |
|---|---|---|---|---|---|
| 0.30 | 1.00 | 1.00 | 1.00 | 1.000 | 0.50 |
| 0.34 | 1.00 | 1.00 | 1.00 | 1.000 | 0.90 |
| **0.345 – 0.365** | 1.00 | 1.00 | 1.00 | **1.000** | **1.00** |
| 0.375 (previous) | 1.00 | 1.00 | 0.95 | 0.988 | 1.00 |
| 0.40 | 0.93 | 1.00 | 0.85 | 0.925 | 1.00 |
| 0.45 | 0.88 | 1.00 | 0.25 | 0.750 | 1.00 |

**Shipped: 0.35**, the middle of the window. At 0.375 the cut chunk was the Offering
Memorandum's asking price, and the generated answer to *"How does the buyer's offer compare
to the asking price?"* then said the documents contain no asking price. At 0.35 the same
question, asked through the live endpoint, cites both $5,859,000 (OM) and $6,085,000 (LOI).

The window is narrow, and it belongs to this corpus and this embedding model. A new
document type or a new model can close it; re-run the fine sweep before trusting it.

### 2. Reranking is the largest single gain

Production floors held fixed (measured at `MinScore 0.375`):

| config | single-fact | table | cross-doc | **overall** | MRR | chars in context |
|---|---|---|---|---|---|---|
| cosine `k=8` | 0.97 | 1.00 | 0.45 | 0.850 | 0.770 | 6,376 |
| rerank `k=8` | 1.00 | 1.00 | 0.85 | 0.963 | 0.794 | 6,327 |
| cosine `k=12` | 1.00 | 1.00 | 0.60 | 0.900 | 0.770 | 8,732 |
| rerank `k=12` | 1.00 | 1.00 | 0.95 | 0.988 | 0.794 | 8,535 |
| **rerank `k=12`, MinScore 0.35 (shipped)** | **1.00** | **1.00** | **1.00** | **1.000** | | |

- Reranking at `k=8` beats plain `k=12` (0.963 vs 0.900) with less context.
- Reranking and a larger `k` still work together: only both together clear every
  cross-document question.
- Recall at fetch (top 20, before filtering) is 1.000 with reranking and 0.988 without, so
  nearly every loss happens *after* the candidates are found. The haystack is small, and the
  problem is ranking within the deal.

### 3. `MaxContextChunks` matters; `RelativeFloor` doesn't

With reranking: `k=5` → 0.912, `k=8` → 0.963, `k=12` → 0.988 (at `MinScore 0.375`). No
other knob moves recall as much.

`RelativeFloor` at `0.00`, `0.35` and `0.55` gives identical recall; `0.55` only trims
context slightly. `0.70` starts losing chunks. Keep `0.55`.

### 4. Ablation: the floors cost nothing and buy all of the rejection

With both floors off, recall is 1.000 but off-domain rejection drops from 1.00 to 0.00: every
nonsense question sends ~11 chunks to the model. `RelativeFloor` can never reject *every*
chunk (its cutoff is `best × 0.55`, which the best chunk always clears), so all the rejection
comes from `MinScore`.

### 5. Latency

Sequential search over the 100 questions, deal-scoped:

| | median | p95 |
|---|---|---|
| cosine only | 0.05 s | 0.07 s |
| cosine + rerank | 2.31 s | 3.35 s |

Reranking is nearly all of the search cost, on CPU. Local bge-m3 is faster than the hosted
OpenAI embedding call it replaced (0.23 s median before).

## Generation

Measured 2026-10-04 on the shipped stack (`MinScore 0.35`), 100 freshly generated answers.
Judged metrics are the mean of 3 passes.

| | result |
|---|---|
| answer states the expected value | **80/80** |
| `Faithfulness` (LLM-judged) | **0.973** ± 0.007 |
| `ResponseRelevancy` (LLM-judged) | **0.716** ± 0.003 |
| `NonLLMContextRecall` | 1.000 |
| `NonLLMContextPrecisionWithReference` | 0.783 |
| `unanswerable` declined by the model | **10/10** |
| `off-domain` declined (no chunks reach the model) | **10/10** |
| answerable questions wrongly declined | 0/80 |

- The value check compares digits for numeric values and whole words (ignoring case and
  punctuation) for values with no digits. Before the word fallback, *"In whose name is title
  currently vested?"* could never pass, since its expected value has no digits; every
  answer set in this doc was re-scored with the fix.
- `Faithfulness` scored 79, 79 and 80 of 80 samples across the three passes (one judge
  timeout in each of the first two); `ResponseRelevancy` scored all 80 every pass.
- `ResponseRelevancy` is lower partly because it penalises the hedging and source
  attribution this system's prompt asks for.

Against earlier stacks:

| | OpenAI embeddings, no rerank, `k=8` | bge-m3 + rerank, `MinScore 0.375` | **shipped** |
|---|---|---|---|
| answer states the expected value | 0.825 | 0.988 | **1.000** |
| `Faithfulness` | 0.932 | — | **0.973** |
| `NonLLMContextRecall` | 0.838 | 1.000 | **1.000** |

**`MinScore 0.375` cost an answer.** An earlier run on this stack, at `MinScore 0.375`, got
*"How does the buyer's offer compare to the asking price?"* wrong: the OM's asking-price chunk
was cut (finding 1), and the answer said the documents give no asking price. At 0.35 it cites
both $5,859,000 (OM) and $6,085,000 (LOI).

**Check the coverage of a judged mean before quoting it.** That earlier run's judge account
ran out of credits mid-run. RAGAS retries the 429s until the job times out, scores the
sample as NaN and averages over the rest, so it printed plausible means over roughly two
thirds of the samples. `eval_ragas.py` now runs the judge at lower concurrency with a longer
timeout, prints how many samples each metric actually scored, and flags any partial mean.

### Abstention: the prompt does the job the floor cannot

A question about the right deal whose answer isn't in the documents scores as high as an
answerable one (top scores 0.40–0.54, against 0.41–0.68 for answerable), so no threshold can
filter it. The system prompt declines it instead: 10/10, with no wrong declines on the 80
answerable questions.

### Cross-checking the two harnesses

RAGAS `NonLLMContextRecall` and `eval_retrieval.py` recall@final measure the same thing and
should agree. Getting them to agree the first time exposed three bugs, all in the harness:

1. RAGAS got only the chunks the answer *cited*, so every score was 0.000. Fix: pass the full
   context, rebuilt with the same search and filter chain.
2. The gold text was a short snippet, which edit distance can never match against a full
   chunk. Fix: use a chunk-sized gold text.
3. That text was a passage cut from the PDF whose edges didn't line up with the real chunk
   (0.300 against a true 0.95). Fix: use the real indexed chunk (`gold_chunk_texts()`).

Lesson: when a judged metric disagrees with a deterministic one, check the harness first.
The judge-credit failure above is the same lesson again: check how many samples a mean
actually covers before quoting it.

### Two notes on judging

- **`FactualCorrectness` was dropped.** It breaks a reference *answer* into claims, but the
  ground truth here is a bare value (`$67,834,000`). Value correctness is checked directly
  instead: the answer must contain the expected value's digits or, for a value with no
  digits, all of its words in order (ignoring case and punctuation).
- **Judged scores vary run to run**, so they are reported as a mean over 3 passes.
  Differences under ~2 points are noise.

## History

How the pipeline got here. The tables in this section were measured on earlier stacks; the
lessons still apply.

### Dense baseline (OpenAI embeddings, no reranking)

The first sweep, at `MinScore 0.15 / RelativeFloor 0.55 / k=8`, measured recall@final 0.80,
with cross-document questions at 0.45. Every cross-document failure had a **full** 8-chunk
context with one of the two required chunks cut. Raising `k` to 12 gave 0.89, and `k` was the
only knob that moved recall. `MinScore` changed no recall between 0.10 and 0.20 but let
*"What is the capital of Mongolia?"* (0.166) into a prompt at 0.15.

### Cross-encoder reranking

Reranking is finding 2 above. Three things were tried around it, re-measured on the shipped
stack in 2026-10 (bge-m3, `MinScore 0.35`, `RelativeFloor 0.55`):

**The reranker model decides most of the result.** `cross-encoder/ms-marco-MiniLM-L6-v2`, a
small popular default, was tried first:

| ordering | `k=8` | `k=12` | cross-doc at `k=12` |
|---|---|---|---|
| cosine | 0.850 | 0.900 | 0.60 |
| `ms-marco-MiniLM-L6-v2` | 0.900 | 0.975 | 0.90 |
| `bge-reranker-base` (shipped) | 0.963 | **1.000** | **1.00** |

MiniLM helps a little, but most of the gain comes from the model, not the technique. It is
also unusable through the proxy route as is: its tokenizer counts some query + chunk pairs at
533 tokens, over its 512 limit, and the route sends no truncation, so those requests fail
with a 422. Its arm was measured by calling the reranker directly with truncation on. In the
original OpenAI-era test MiniLM made recall *worse*, which was only visible because
`rerankScore` is returned as a diagnostic field.

**Diversity reranking (MMR / per-document quota) is the wrong operator.** Simulated with
[`analyze_diversity_sim.py`](../scripts/analyze_diversity_sim.py) on the 10 cross-document
questions whose sources are fetched but cut at `k=8` in cosine order: the best MMR setting
fixes 1 of 10 and makes 6 worse; a per-document quota fixes none. The cross-encoder fixes 8 of
the 10. Cross-document questions need two chunks stating the *same* fact, and MMR demotes
exactly those near-duplicates. The stage was removed.

**Without the `dealId` filter, ranking isn't the problem.** Searching the whole corpus
instead of one deal, only 0.175 of the needed chunks are even fetched in the top 20.
Reranking can't recover that (0.075 at `k=8` either way, 0.113 → 0.138 at `k=12`), and half
the off-domain questions get through `MinScore 0.35`, because the best match anywhere in the
corpus scores higher than the best match in one deal. A cross-deal search needs metadata
filtering and its own floor before reranking matters. (In the OpenAI era reranking made the
unscoped case slightly worse, 0.100 → 0.062; on bge-m3 it no longer does.)

How it is built:

- Search, rerank the top 30, then cut to `topK` once at the end
  ([`app/api.py`](../src/IngestionService/app/api.py)).
- **`score` stays cosine.** Reranking only sets `rank`, so the floors stay calibrated and
  off-domain questions still fail `MinScore`. `rerankScore` is diagnostic.
- `rerank_candidates=30` is fixed, never derived from `topK`; the eval's fetch cache relies
  on this.
- On failure, search keeps the cosine order and returns `rerank: false`.
- Chunks stay at 300 tiktoken tokens. The largest is 350 reranker tokens, under the 512
  limit. Re-measure before raising `chunk_size`.

### BM25 keyword search, removed

BM25 keyword search in a separate OpenSearch index, fused with the pgvector results, was
built and measured. With reranking on, adding it changed no metric: the cross-encoder
subsumed whatever BM25 contributed to ordering. The index kept
a second full copy of the corpus (dual writes, backfill, sync), so it was removed. If a
lexical signal is wanted again, Postgres full-text search on the existing `text` column needs
no second store.

### Embeddings: OpenAI → bge-m3

Embeddings moved to `bge-m3` on the local `tei-embedding` container, for cost and data
residency.

**`MinScore` has to be re-tuned for each embedding model, and nothing warns you if it isn't.**
Under bge-m3, *"How do I bake sourdough bread?"* scores 0.39 (0.09 under OpenAI). The old
0.15 floor let every off-domain question through while recall stayed at 1.000, so nothing
looked wrong; Deal Q&A just started answering questions it shouldn't.

The first bge-m3 floor was 0.375, chosen from an earlier, coarser sweep. An earlier
estimate of 0.35–0.40 had been made offline from each question's *top* score, which misses
chunks dropped inside questions that still get answered. Sweep with the harness before
trusting a threshold; finding 1 above is that sweep, on the shipped stack.

Operational notes:

- bge-m3 needs ~4 GB and the reranker ~3.7 GB. Give Docker ~12 GB, or one container
  OOM-kills the other.
- [`app/reembed.py`](../src/IngestionService/app/reembed.py) recomputes vectors from stored
  chunk text (~8 minutes for 1,147 chunks). Only valid while chunking is unchanged.
- Both models' vectors coexist (the unique key includes `embedding_model`), so switching
  back is a config change plus the matching `MinScore`.

## Limitations

- **The haystack is small.** A deal has ~17 chunks and `FetchTopK = 20` fetches nearly all
  of them, so recall@fetch ≈ 1 is close to free. The real problem is ranking within the deal.
- **One templated corpus.** Templated PDFs make extraction easy, and the `MinScore` window
  is specific to it. Real documents are messier.
- **Small slices are noisy.** 20 questions per slice, so one failure moves a slice 5 points.
  The `MinScore` window is decided by a single cross-document chunk and a single off-domain
  question.
- **Generated questions share the generator's phrasing**, despite paraphrasing.
- **Cross-deal search is not evaluated.** Every question is deal-scoped. The assistant's
  `search_deal_documents` tool can search without a deal, a path this eval never exercises.

## Reproducing

Requires the stack up with documents seeded and Docker at ~12 GB:

```bash
docker compose --profile local-embeddings up -d
```

Rebuild the question set (only when the corpus changes):

```bash
python3 scripts/rebuild_manifest.py && python3 scripts/build_eval_set.py
```

Regression gate (run before and after any retrieval change):

```bash
python3 scripts/eval_retrieval.py --rerank --out /tmp/regress.json && python3 scripts/check_retrieval_regression.py /tmp/regress.json
```

After an intended, measured change, refreeze the reference:

```bash
python3 scripts/check_retrieval_regression.py --freeze /tmp/regress.json
```

Parameter sweep with reranking, and the rerank A/B:

```bash
python3 scripts/eval_retrieval.py --sweep --rerank
```

```bash
python3 scripts/eval_retrieval.py --sweep-rerank
```

Single arm at a chosen floor:

```bash
python3 scripts/eval_retrieval.py --rerank --min-score 0.35
```

Generation. Needs its own venv (`scripts/requirements-eval.txt`), and ai-service's rate
limit off for 100 questions:

```bash
AI_RATE_LIMIT_ENABLED=false docker compose up -d ai-service
```

```bash
scripts/.venv/bin/python scripts/eval_ragas.py --rerank --regenerate
```

The LLM-judged metrics are opt-in and cost ~1,440 judge calls. Check the
"only N/80 samples scored" warning before quoting them:

```bash
scripts/.venv/bin/python scripts/eval_ragas.py --rerank --llm-judge --repeats 3
```

Turn the rate limit back on afterwards:

```bash
docker compose up -d ai-service
```

Raw results from the 2026-10 re-evaluation are in `scripts/eval-archive/` with a
`2026-10-reeval` prefix.
